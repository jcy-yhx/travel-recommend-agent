## 1 分钟版本（约 250 字）

我做的是一个从零演进的 AI 旅游规划 Agent，技术栈是 Vue3 + Express + LangGraph + SiliconFlow 的 DeepSeek。

核心流程：用户给目的地、预算、天数 → LangGraph 图里的 Agent 循环自主调用天气和景点检索工具 → planner 先出大纲锁定预算 → executor 展开完整行程 → 两层校验（zod 格式 + 规则语义），失败就带反馈重来一次 → 结果结构化返回并写入会话状态，支持多轮追问"把第二天改成西湖"。

三个我想强调的数字：第一，重写编排时——手写循环换成 LangGraph 图，之前 48 个测试一个没改全部通过；第二，检索从关键词升级到语义 embedding，同一批 8 个评测用例从命中 1 个变成 8 个；第三，端到端评估第一轮 6 个用例失败了 2 个，定位到检索预算约束太软，修复后全绿，judge 平均 4.33 分。

## 3 分钟版本（结构 + 每段要点）

### ① 为什么做（30 秒）

> 目标不是做一个 CRUD 项目，而是通过真实项目把 Agent 的核心概念全部亲手实现一遍。所以项目的独特价值是"演进史"：每一步都有"之前有什么问题 → 加了什么 → 数据证明有效"。

### ② 系统现在长什么样（45 秒）

> 讲架构图：前端 Vue3 → Express（限流/错误处理）→ LangGraph 8 节点图（agent↔tools 循环、planner→executor→validator、re-plan 条件边）→ 结果写会话状态。工具：天气（Mock）+ 景点语义检索（bge-m3，本地索引）。

### ③ 三个最有故事的技术决策（60 秒，选讲 2-3 个）

1. **手写 vs 框架**：Phase 03 手写 Agent Loop（双终止条件 + max_iter），Phase 07 才用 LangGraph 重写——所以我能说清框架替我做了什么（循环=两条边、终止=条件路由），而不是"用了但我不知道为什么"。旧测试原样通过是重写正确性的证明。
2. **克制清单**：没上向量库（22 条数据暴力扫描毫秒级）、没上 Redis（单机 JSON 够用）、没启用 checkpointing——每一条"没做"都有理由，这是工程判断力。
3. **eval 迭代故事**：第一轮端到端评估 6 用例失败 2 个（三亚/西安触发 max_iter），定位到"检索预算约束太软"，改成硬性约束后全绿。**eval 的价值就是抓问题**。

### ④ 真实踩坑（45 秒，选 1-2 个）

> - `response_format json_object` 与 `tool_choice required` 在同一实例上冲突，LangChain 抛误导性错误，用裸 API 调用隔离定位根因 → 双实例架构
> - 模型对空检索结果反复换关键词搜索不停手，max_iter 兜底 24 秒干净失败——工具话术"请尝试其他关键词"在鼓励它继续搜

### ⑤ 收尾（15 秒）

> 项目还配了完整的学习文档（9 个 Phase，每个含踩坑记录和面试问答）。我最想被追问的部分是 eval 体系——它是怎么抓到问题的，以及 judge 的局限。

## 每个技术点的"为什么"一句话

- **zod**：字段级错误信息能直接反馈给模型驱动重试
- **双 LLM 实例**：json_object 与 tool_choice 实测冲突，职责分离
- **tool_choice required 首轮**：auto 模式实测会跳过工具用参数记忆
- **max_iter = 5**：保险丝不是常态出口（自主终止才是）
- **JSON 文件持久化**：规模没到，演进路径明确（Redis/DB）
- **不上向量库**：22 条暴力扫描毫秒级，向量库解决另一个量级的问题
- **re-plan 只一次**：一次修正是保险丝，多轮迭代是 Reflexion 的成本陷阱
- **LLM-as-judge**：规则校验的边界（150 元案例住宿 0 元也通过），现实层必须模型判断
