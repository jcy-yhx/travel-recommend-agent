应包含的规则（新增）
A. 阶段边界（防跨 Phase / 防自作主张）

「一次只做当前 Phase 的验收目标。发现其他问题 → 记录到 PROGRESS.md 的 Backlog，不顺手实现、不顺手重构。」——必须明确写出"发现也不修"，否则 AI 必然"顺手优化"
「禁止新增依赖，除非该依赖在 Phase 文档中明确点名。想引入框架先停下询问。」——防 MCP/向量库/新框架渗透
「禁止重构。只允许：实现验收目标 + 修复你本次改动直接引起的错误 + 修复构建失败。」——"重构"一词必须定义，否则 AI 会把它解释为"让代码更漂亮"
冲突优先级条款：「修复构建失败/进程崩溃 > 阶段边界规则。修复后必须在 PROGRESS.md 记录越界内容。」——不加这条，AI 会在"不许碰别的"和"build 坏了"之间死锁或偷偷越界
B. 测试与验证（防 AI 声称完成）
5. 「每个验收目标必须有真实运行的测试/验证命令及其真实输出贴进 Phase 文档。禁止写"测试通过"四个字而不贴输出。」
6. 「LLM 相关改动必须用真实 API 调用验证至少一次成功 + 一次失败路径。」——失败路径是 AI 最容易跳过的

C. 文档生成
7. 「学习文档只写本 Phase 的代码区域，引用真实代码片段（含行号），禁止粘贴泛泛概念。测试章节必须填真实用例与真实输出。」
8. 「"动手练习"的 Level 2/3 和"必须会说的话"留空，由用户填写。AI 禁止替用户写答案。」——这条极其重要，见 §7
9. 「文档生成后立即停止，输出阶段总结，不做任何超出 Phase 的后续动作。」——"立即停止"要写成一个独立动作

D. 进程管理
10. 「PROGRESS.md 的 User Confirmation 字段只允许用户修改。AI 看到 PENDING 时本 Phase 未结束，不得继续下一 Phase。」
11. 「每个 Phase 结束时 git commit，commit message 带 phase 编号。」——git 历史本身就是学习轨迹，也是面试时"演进叙事"的证据链（当前 docs/ 还没进 git，是个隐患）

应避免的规则（如果模板或你将来想加，删掉）

特别检查：会不会过度 Agent 化？
会，而且你的担心完全成立。 当前路线最大的诱惑是：旅游项目 → LangGraph → RAG → Memory → Reflection → （下一步必然有人建议）MCP → Multi-Agent → 向量库。每加一层，项目复杂度翻倍，学习收益递减，面试被问穿概率翻倍。

明确的分界线：

应该做：LLM 调用 → Structured Output → Tool Calling → Agent Loop → State（内存+JSON）→ 小型 Eval 集 → 预算一致性 Validator。到 Phase 03 结束你就拥有一个真 Agent；到 04+eval 你就有了面试弹药。

Phase 00 — 项目理解与跑通

当前问题：模板内容与本阶段实际任务脱节。本阶段真实工作是：修崩溃 bug、补 detail 渲染、消费 SSE、删脚手架、加 smoke test、画数据流

修改原因：Phase 00 是最容易"走过场"的阶段（"跑通了，下一个"），必须绑定真实 bug 修复才有学习密度。本阶段可以快速完成，但产出必须实打实
Phase 01 — Structured Output

当前问题：只有一句目标。缺关键决策：SiliconFlow 的 DeepSeek 模型是否支持 response_format JSON mode / tool forcing？这决定实现路线（JSON mode vs tool-calling 强制 vs zod+重试）
建议：文档中必须先写"技术选型验证"小节（实测模型能力）；实现 zod/schema 校验 + 失败重试 ≤2 次 + temperature 分区；补 eval 用例 3 个（含"模型输出尾随文本"这个当前真实失败场景）
修改原因：这是全路线最值得深入的 Phase 之一（面试必问），也是修复现有代码真实缺陷的 Phase
Phase 02 — Tool Calling

当前问题：目标句正确但没限定工具集
建议：限定 2-3 个工具（get_weather 用 Mock 数据、search_attractions 查本地 JSON、get_route 规则生成）；必讲：schema 设计、参数校验、调用失败处理、tool_choice 控制
修改原因：工具必须少而真实。Mock 天气是正确决策（学习目标在 Agent 机制不在天气数据），但要写明 Mock 与真实 API 的替换点
Phase 03 — Agent Loop

当前问题：目标句是全路线写得最好的一句（"亲手实现最小 Agent Loop"）
建议：手写 loop（不用 LangChain Agent 封装）；必须覆盖：终止条件（max_iter + LLM 自行 stop）、工具异常后的恢复、无限循环防护；毕业标准加"口述循环机制"
修改原因：这是项目的"Agent 时刻"，也是面试主战场。值得投入全路线最多的时间之一
Phase 04 — State / Memory

当前问题：State 和 Memory 混在一个 Phase，概念边界不清
建议：文档中明确区分：State = 单次任务内的规划状态（内存）；Memory = 跨会话信息（先 JSON 文件持久化对话历史即可）。不上数据库、不上向量记忆
修改原因：面试官最爱问"State 和 Memory 有什么区别"——如果你自己文档都混着写，必被问穿
Phase 05 — RAG

当前问题：旅游场景知识库需求弱，最容易滑向"为了 RAG 而 RAG"
建议：降级为 RAG-lite：10-20 条本地景点 JSON + embedding 检索（SiliconFlow 有 embedding API）；明确写"为什么不上向量库"
修改原因：保留"为什么不用向量库"这个克制的答案，比真正上向量库更有面试价值。时间紧可压缩到 1 天
Phase 06 — Planning / Reflection

当前问题：范围无边界，学术化风险高
建议：压缩为三个动作：plan-then-execute prompt 结构 + 预算一致性 validator（模型输出的 totalBudget/明细 vs 用户输入预算）+ 校验失败时 re-plan 一次。validator 顺便解决当前代码的另一个真实缺陷（LLM 输出与预算不符无人管）
修改原因：一次 re-plan 就是 Reflection 的教学版本，足够面试使用
Phase 07 — LangGraph

当前问题：目标句写"工程化为图结构"，但没有"为什么"
建议：毕业标准 = 用 LangGraph 重写 Phase 03 的 loop，并写出对比（checkpoint/持久化/可视化/条件边各自解决了手写版的什么问题）；写不出来 = 不过
修改原因：这是全路线最容易被面试官问穿的一环（"手写 loop 不是够了吗？"）。答案不真实就不该做
Phase 08 — Production / Interview（建议拆分，见 §5）

当前问题：一锅炖，必然是走马观花
建议：拆为 08 Eval & Hardening + 09 Interview Prep；Eval 集从 Phase 01 起每 Phase 攒 3 个用例，到 08 成型
修改原因：Eval 是面试差异化王牌，值得独立 Phase；面试准备是独立技能，值得独立时间
7. 学习机制修改建议
你的模式（AI 开发 → AI 写文档 → 你看 → 练习 → 答题 → 确认）方向对，但有一个致命假设：你看完 AI 写的文档和代码，就认为自己懂了。 认知心理学上这叫"熟悉感错觉"——阅读产生流畅感，流畅感被误认为掌握。你模板里其实已经有了药方（§15 动手练习、§18 毕业检查），但没有任何机制保证你真的做了。

必须把"毕业检查"从"自评清单"升级为外部门禁：

门禁	机制（AI 充当执行者）	防什么	频率
运行门禁	你亲手跑项目，亲手复现一次成功 + 一次失败场景，贴输出	"AI 说能跑"	每 Phase
改码门禁	Level 2 练习由你改代码提交 diff；AI 只点评不改	只读不写	每 Phase
重写门禁	Level 3：关掉 AI，从空文件重写本 Phase 核心代码（如 Phase 03 的 loop）	"看着都懂"	核心 Phase（01/03/08）
Debug 门禁	AI 在本 Phase 代码里注入 1 个 bug，你定位并修复，全程不求助	不懂调试（面试必考）	每 Phase
口述门禁	不看任何笔记，5 分钟讲数据流；AI 追问 3 个问题，答不上即不过	"我以为我懂了"	每 Phase
小考门禁	AI 出 5 题：2 概念 + 1 改错 + 2 项目追问；错 1 题 → 复习后重考	记忆错觉	每 Phase
确认门禁	你在 PROGRESS.md 亲手写 PENDING→PASS + 日期；AI 禁止触碰该字段	AI 替你确认	每 Phase
面试模拟	AI 当面试官 10 分钟追问本 Phase 内容，录音回听	表达不清	Phase 03 起，每 2 周
其中 Debug 门禁（AI 注入 bug）是成本最低、收益最高的机制——它把你从"读者"变成"修理工"，而面试问的正是"你修过什么"。

另外，AI 生成文档的质量约束（写进 AGENT.md）：文档必须含本 Phase 真实代码片段、真实测试输出、真实踩坑记录（哪怕丑），禁止粘贴泛概念。一份带真实失败案例的文档，比十份干净的概念文档更防错觉。

9. 最终推荐架构
根据评审结论，克制版最终形态（每层都对应一个 Phase 的产出）：


User（Vue3 + Vant 移动端）
   │  POST /api/travel/plan（SSE 可选：进度事件）
   ▼
Express 路由层 ── 参数校验 · asyncHandler · 全局错误中间件     ← Phase 00
   ▼
TravelAgent（核心：Agent Loop，max_iter 终止 + 异常恢复）      ← Phase 03
   ├── AgentState（内存；JSON 文件持久化对话历史）             ← Phase 04
   ├── Tool Registry（白名单工具）                            ← Phase 02
   │      ├─ get_weather         ← Mock 数据，可替换真实 API
   │      ├─ search_attractions  ← 本地 JSON + embedding 检索（RAG-lite） ← Phase 05
   │      └─ get_route           ← 规则生成
   ├── LLM 层（OpenAI 兼容接口 / SiliconFlow）
   │      ├─ Planner Prompt      ← plan-then-execute 结构      ← Phase 06
   │      ├─ Structured Output   ← JSON schema 校验 + 失败重试 ≤2  ← Phase 01
   │      └─ temperature 分区：规划 0.7 / 结构输出 0~0.2
   └── Validator（预算一致性 + 天数匹配；失败 re-plan 一次）   ← Phase 06
   ▼
响应 → 前端渲染行程（detail 页完整渲染）                        ← Phase 00
   ▲
Eval 集（≥15 用例 + rubric，离线评估，不进运行时）             ← Phase 01-08 积累
明确不在架构里的：向量数据库、Redis、MCP Server、Multi-Agent 编排、微服务。LangGraph（Phase 07）是可选替换层：用图结构重写同一个 TravelAgent，价值仅在 checkpoint/持久化/可视化。
